# 国区版版本发布

本文件用于指定版本的发布与流程恢复。发布授权范围、Git 操作边界和完成标准以根 [`AGENTS.md`](../AGENTS.md) 为准；查阅或准备发布流程本身不触发发布。

## 事实来源与流程恢复

- 当前源码和配置决定版本、发布布局与更新协议：`AssetEditor/AssetEditor.csproj`、`AssetEditorUpdater/AssetEditorUpdater.csproj`、`AssetEditor/Properties/PublishProfiles/FolderProfile.pubxml`、`AssetEditorUpdater/GiteeUpdateSource.cs` 和 `.github/workflows/pr-test.yml`。
- 已有 Release 和远端资产只用于核对命名、结构及发布操作，不能替代当前源码和本次产物的验证。不要照抄旧版的文件大小、分片数或哈希值。
- `publish-asseteditor-cn` Skill 存在时可作为操作指引。若 Skill 不可用，依据本文件与当前配置恢复具体步骤；遇到无法核实的工具、权限、产物契约或远端状态，完成不依赖该信息的准备并在对应写入前停下说明。

## 构建模式与版本号

- 本地开发、调试、日常验证和人工验收使用项目正常输出目录中的 `Debug`。
- 线上 CI 使用 `Release`：`.github/workflows/pr-test.yml` 中 PR、`master` 推送及手动触发的自动构建与测试保持同一配置。CI 的 `Release` 仅表示编译配置，不执行正式发布，也不自动授予发布权限。
- 用户明确要求正式发布指定版本后，使用 `Release` 完成发布验证与打包。`FolderProfile.pubxml` 的正式发布配置继续保持 `Release`；发布准备阶段同步主程序、更新器及 `README.md` 的版本，不自行递增。
- 日常提交、推送和合并不自动升级版本号，也不触发正式发布。

## 发布顺序与门禁

1. 核对仓库、`master`、完整 Git 状态、远端最新提交、最近正式版本和目标标签。只使用用户指定的版本号；已有同名标签或不明工作区改动先处理清楚。
2. 同步检查主程序与更新器项目中的 `<Version>`，以及根 `README.md` 的“当前版本”；核对产品名、可执行文件名、用户目录和 Gitee 更新源未偏离国区版身份。根据上一版本到目标提交的实际差异编写发布说明。
3. 执行根 `AGENTS.md` 中正式发布的完整 Release 还原、构建和测试。随后在全新暂存目录按 `FolderProfile.pubxml` 发布；`AssetEditor.csproj` 的 `PublishUpdater` 目标应把独立更新器放入发布目录的 `Updater/`。核验主程序、更新器、运行时文件及目录结构，再按下节的 Bandizip 规则打包完整安装 ZIP。
4. 核对更新协议后准备 Gitee 资产。更新器要求同一发行版恰好有一个 `.manifest.json` 清单，以及清单中每个分片各一个 ZIP 资产；清单包含版本、完整 ZIP 的名称/大小/SHA-256，和按顺序列出的分片名称/大小/SHA-256。分片大小与哈希、合并后的完整 ZIP 大小与哈希都必须由本次实际产物计算并验证；分片应符合 Gitee 当时的附件限制。不要固定分片数量。发布前用不带登录态和令牌的请求检查上一已发布版本实际使用的 Gitee 版本查询入口；若入口返回 403、429 或其他失败，先停止发布，不反复请求。
5. 在根 `AGENTS.md` 的授权范围内执行必要提交、推送、标签、GitHub Release 和国区更新源发布。GitHub Release 提供完整安装 ZIP；Gitee 发行版提供清单与分片。资产全部上传并验证后，更新 Gitee 仓库 `master` 的 `update-feed.json`：文件是单个最新发行版对象，包含 `tag_name`、`name`、`body`、`created_at` 和 `assets`，资产仅列出本次清单与分片的 `name`、`browser_download_url`，不含令牌。任何阶段失败即停止，不跳过或声称已完成后续阶段。
6. 回读远端提交与标签、GitHub Actions 最终状态、GitHub Release 的版本/说明/资产，以及 Gitee 发行版的版本/清单/分片。管理接口可使用发布凭据；随后必须清除凭据和登录态，使用上一已发布版本的主程序及更新器走真实公开路径，确认能发现目标版本、下载清单与全部分片、验证哈希，并在全新隔离目录完成安装。还要匿名读取 `update-feed.json`，确认它指向目标版本及本次资产。公开入口受限或任何一步失败时停止并报告，不能用带凭据的回读、当前源码单元测试或手动下载代替。全部通过后才报告发布完成。
7. 新版本发布并完成上述验收后，再按“Gitee 版本保留”清理最旧发行版，使保留数量不超过三个。发布验收与旧版清理的结果分别报告；清理待批准或失败时保留现状，不把待处理的删除描述为已完成。

## Bandizip 完整安装包

- 使用 Bandizip 压缩已经核验的整个 `AssetEditor.CN` 文件夹，输出格式为 ZIP，目标目录固定为 `D:\WH3 Modding Tool\Compressed`。打包时只包含本次正式 Release 发布产物，保留主程序、`Updater/` 和所需运行时文件。
- 文件名严格为 `AssetEditorCN <版本号>.zip`，`AssetEditorCN` 后接一个半角空格，再接用户指定的版本号。例如版本 `2.5.2` 的完整路径为 `D:\WH3 Modding Tool\Compressed\AssetEditorCN 2.5.2.zip`；示例不构成发布或修改版本号的指令。
- ZIP 内保留顶层文件夹层级：`AssetEditor.CN/AssetEditor.CN.exe`、`AssetEditor.CN/Updater/AssetEditor.CN.Updater.exe` 及同层其他发布文件。压缩后检查完整性与目录结构，并从这个实际 ZIP 计算清单所需的大小和 SHA-256。
- GitHub Release 上传该完整 ZIP；Gitee 仍按既有协议上传对应清单与 ZIP 分片。分片合并必须还原同一个完整 ZIP，不改变完整包的名称、内容和目录层级。

## Gitee 版本保留

- 仅在新版本发布及全部既有验收成功后执行。重新读取实际发行版列表，按版本号与发布日期交叉核对，从最旧版本开始选择清理对象，最终最多保留三个版本；已有不超过三个版本时不删除。版本号与日期矛盾或先后关系不明确时，先报告具体差异，不按列表顺序或版本字符串的字典序猜测。
- 清理前再次核对最新发行版、`update-feed.json` 指向的版本及其资产；这些版本都必须保留。明确列出拟删除发行版的版本号、发布日期、链接及随之删除的资产，避免只删除部分清单或分片而留下不可用发行版。
- 若删除不可恢复，执行前把完整清理清单集中交给用户明确批准，取得针对这些对象的批准后才执行。本文件描述保留策略，不是预先批准不可恢复删除；不得借发布请求或已上传成功绕过确认。
- 若上传新版本之前已受存储或附件配额阻挡，停止对应上传，报告服务返回的限制与当前版本情况，不擅自把顺序改为先删除旧版再发布。
- 清理后回读发行版列表和 `update-feed.json`，确认保留数量、最新版本及更新源引用正确。清理失败或待批准时如实报告剩余对象，保留已通过的发布验收记录。

本文件记录稳定门禁，不保存临时凭据、某次发布的提交号、文件大小、分片数量或哈希值。发布的实际命令、输出和未完成环节在当次对话中报告。
